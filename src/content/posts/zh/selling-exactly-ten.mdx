每个库存系统迟早都会遇到同一个下午：某件商品只剩 10 件，营销邮件发出去了，40 个人在同一秒里按下“购买”。问题不在于你的代码能不能正确处理一个订单，而在于它能不能同时正确处理 40 个。

[OrderPilot](/zh/projects/orderpilot/) 里有一个测试专门模拟这个下午：它在容器中的真实 MySQL 上启动 40 个线程，每个线程都想买库存为 10 的同一件商品，最后断言订单恰好是 10 个。这篇文章讲的，就是让这个测试通过的那一行代码。

## 人人都会先写出的代码

库存检查的第一版写起来很自然：

```java
int available = jdbc.queryForObject(
    "SELECT available FROM inventory WHERE sku = ?", Integer.class, sku);
if (available >= qty) { // [!code highlight]
    jdbc.update("UPDATE inventory SET available = ? WHERE sku = ?", available - qty, sku);
    createOrder(sku, qty);
}
```

单独看每个请求都没错，问题出在 `SELECT` 和 `UPDATE` 之间的空隙。两个请求可能读到同一个数字，都判断库存够用，又都写回同一个结果：

两个买家时，多卖了一件。40 个买家时，竞争会层层叠加：每次写入依据的数字都可能已经过时，以至于当一个慢请求写回旧值时，库存甚至会*上涨*。[项目案例中的交互实验](/zh/projects/orderpilot/#demo)运行的正是这段逻辑，通常会卖出二三十件根本不存在的库存。

## 让数据库来做检查

修复的关键，是不再“先问数据库一个问题，再根据答案行动”，而是让它一次把两件事都做完：

```java title="InventoryService.java"
int rows = jdbc.update("""
    UPDATE inventory
       SET available = available - ?
     WHERE sku = ? AND available >= ?""", qty, sku, qty); // [!code highlight]
if (rows == 0) throw new InsufficientStock(sku);
```

InnoDB 在执行 `UPDATE` 时会锁住这一行，并用最新提交的版本来判断 `WHERE` 条件，所以检查和扣减无法被拆开。库存耗尽后，条件不再成立，语句影响 0 行，代码就知道自己没抢到。其他请求根本没有插进来的空隙。

<Callout type="tip" title="影响行数就是答案">
语句影响的行数就是全部结果：1 表示抢到了库存，0 表示没有。不需要第二次查询，也就没有竞争。
</Callout>

## 让保证真正成立的细节

一条语句解决了单个商品的问题。真实的订单往往有多行，还需要几个细节，才能让这个保证对它们同样成立。

**整个订单一个事务。**每一行的 `UPDATE`、订单记录以及它的 Outbox 事件一起提交。如果第三行库存不足，异常会回滚第一、二行，不会有人为一个不存在的订单占着库存。

**按固定顺序加锁。**两个多行订单如果以相反的顺序操作同样的商品，就可能死锁：各自持有一行，等待对方那一行。预占之前先按商品 ID 排序，所有事务都按同样的顺序申请锁，环路就无从形成。

**约束是最后一道防线。**表上带有 `CHECK (available >= 0)`。[^1] 如果将来有改动绕过了条件更新，数据库会拒绝这次写入，而不是悄悄变成负数。

## 我没有选择的方案

常见的替代方案，各有这个方案没有的代价。先 `SELECT … FOR UPDATE` 再更新，持有的是同一把锁，却要两次往返。基于版本号的乐观重试，会把热门商品变成一场重试风暴。用 Redis 加 Lua 脚本预扣减可以扛住更大的规模，但随之而来的是两个数据源之间的对账，只有到了秒杀级别的流量才划算。

对一家店铺来说，条件 `UPDATE` 是少见的、既最简单又可以证明正确的方案。证明它的测试也很短：40 个线程、10 件库存，以及一条断言——订单恰好是 10 个。

[^1]: MySQL 从 8.0.16 起才会真正执行 `CHECK` 约束，更早的版本会解析它，但默默忽略。
