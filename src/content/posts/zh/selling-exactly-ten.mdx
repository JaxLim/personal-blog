每个库存系统迟早都会碰上这样一个下午：某件商品只剩 10 件，营销邮件刚发出去，40 个人在同一秒按下“购买”。关键不在于代码能不能处理好一个订单，而在于 40 个订单同时涌进来时，它还能不能处理对。

[OrderPilot](/zh/projects/orderpilot/) 里有一个测试专门模拟这个下午：它在容器中的真实 MySQL 上启动 40 个线程，每个线程都想买库存为 10 的同一件商品，最后断言订单恰好是 10 个。这篇文章讲的，就是让这个测试通过的那一行代码。

## 大家第一反应写出的代码

库存检查的第一版写起来很自然：

```java
int available = jdbc.queryForObject(
    "SELECT available FROM inventory WHERE sku = ?", Integer.class, sku);
if (available >= qty) { // [!code highlight]
    jdbc.update("UPDATE inventory SET available = ? WHERE sku = ?", available - qty, sku);
    createOrder(sku, qty);
}
```

单独看每个请求都没错，问题出在 `SELECT` 和 `UPDATE` 之间的空隙。两个请求可能读到同一个数字，都判断库存够用，又都写回同一个结果：

两个买家，多卖一件；换成 40 个买家，冲突就会一层叠一层：每次写入依据的数字都可能早已过时，一个慢请求写回旧值时，库存甚至会*不降反升*。[项目案例里的交互实验](/zh/projects/orderpilot/#demo)跑的正是这段逻辑，通常会多卖出二三十件根本不存在的库存。

## 让数据库来做检查

解决办法是：别再“先问数据库，再根据答案行动”，而是让数据库一步把检查和扣减都做完：

```java title="InventoryService.java"
int rows = jdbc.update("""
    UPDATE inventory
       SET available = available - ?
     WHERE sku = ? AND available >= ?""", qty, sku, qty); // [!code highlight]
if (rows == 0) throw new InsufficientStock(sku);
```

InnoDB 在执行 `UPDATE` 时会锁住这一行，并用最新提交的版本来判断 `WHERE` 条件，检查和扣减因此成了一个拆不开的整体。库存一旦耗尽，条件就不成立，语句影响 0 行，代码由此知道自己没抢到。别的请求根本插不进来。

<Callout type="tip" title="影响行数就是答案">
语句影响的行数就是全部结果：1 表示抢到了库存，0 表示没有。不用再查一次，自然也就没有竞争。
</Callout>

## 让这个保证真正站得住的几个细节

一条语句解决了单个商品的问题。但真实订单往往包含好几个商品，还得补上几个细节，多行订单才能有同样的保证。

**整个订单一个事务。**每一行的 `UPDATE`、订单记录以及它的 Outbox 事件一起提交。如果第三行库存不足，异常会回滚第一、二行，不会出现为一个并不存在的订单占着库存的情况。

**按固定顺序加锁。**两个多行订单如果以相反的顺序操作同样的商品，就可能死锁：各自持有一行，等待对方那一行。预占之前先按商品 ID 排序，所有事务都按同样的顺序申请锁，也就不会形成循环等待。

**约束是最后一道防线。**表上带有 `CHECK (available >= 0)`。[^1] 如果将来有改动绕过了条件更新，数据库会拒绝这次写入，而不是悄悄变成负数。

## 为什么没选其他方案

常见的几种替代方案，都有这个方案没有的代价。先 `SELECT … FOR UPDATE` 再更新，锁还是同一把，却要多一次往返。基于版本号的乐观重试，会让热门商品陷入一场重试风暴。用 Redis 加 Lua 脚本预扣减能扛住更大的流量，但代价是两份数据之间的对账，只有到了秒杀级别才划算。

对一家普通店铺来说，条件 `UPDATE` 难得地做到了既最简单、又能证明正确。证明它的测试也很短：40 个线程、10 件库存，外加一条断言：订单恰好 10 个。

[^1]: MySQL 从 8.0.16 起才会真正执行 `CHECK` 约束，更早的版本虽然能解析，却会直接忽略。
