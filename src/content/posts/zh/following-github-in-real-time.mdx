首页上有一条轨迹，记录了我最近十三周推送的所有内容，旁边还有一行文字描述我最新的动态。只要页面开着，它们就会自动更新。背后没有服务器，没有数据库，也没有接收 Webhook 的服务——整个网站就是纯静态的 HTML。

这篇文章介绍它的实现方式，以及我为什么选择这种结构，而不是其他方案。

## 两个部分：快照与数据流

数据分两步到达页面。

1. **构建时**，Astro 调用一次 GitHub API，获取我的仓库和最近的动态，直接渲染进 HTML。即使访客关闭了 JavaScript，也能看到完整的页面，搜索引擎收录的也是真实内容。
2. **在浏览器中**，一个小模块接着快照继续工作。它向 GitHub 询问构建之后的新内容，再把新动态合并到页面里。

快照以 JSON 的形式嵌入页面，浏览器不需要再请求一次：

```astro
---
const json = JSON.stringify(data).replace(/</g, '\\u003c');
---
<script is:inline type="application/json" id="github-data" set:html={json} />
```

转义 `<` 很重要：否则，一条包含结束 script 标签的提交信息就会提前结束这个标签。

## 克制地轮询

GitHub API 对匿名请求的限制是每个 IP 每小时 60 次。如果页面每隔几秒轮询一次，几分钟内就会用完额度，所以这个模块遵守几条规则。

### 条件请求

每个响应都带有 `ETag`。下一次请求时把它放进 `If-None-Match` 发回去，如果内容没有变化，GitHub 会返回空的 `304 Not Modified`。

```ts
const headers: Record<string, string> = { Accept: 'application/vnd.github+json' };
const etag = state.etags[path];
if (etag) headers['If-None-Match'] = etag;

const res = await fetch(API + path, { headers, cache: 'no-cache' });
if (res.status === 304) return null; // 没有新内容
```

### 让 GitHub 决定节奏

动态接口会返回 `X-Poll-Interval` 响应头，通常是 60 秒。轮询的频率从不超过这个值；它还会读取 `X-RateLimit-Remaining`，额度快用完时就完全停下来。

### 没人看时就暂停

标签页被隐藏时，轮询会停止。读者回来时，如果已经超过间隔，就立即补上一次。

<Callout type="tip" title="为什么不用 Webhook？">
Webhook 是即时的，但需要一台服务器来接收，还需要某种方式把变化推送给打开的页面。对个人网站来说，一分钟的延迟换来不必运行任何基础设施，是值得的。
</Callout>

## 让轨迹可信

这条轨迹统计的是*贡献*，而不只是提交：一次推送按其中的提交数计算，创建拉取请求、提交议题或发布版本各算一次。给别人的仓库点星不算在内。

如果构建时提供了 GitHub 令牌，它会改用 GraphQL API 获取精确的贡献日历。那正是 GitHub 个人主页上绿色方格的数据，如果个人主页设置为显示，还会包含私有仓库的贡献。

| 数据来源 | 需要令牌 | 包含私有仓库 | 每日数据准确 |
| --- | --- | --- | --- |
| 公开动态 API | 否 | 否 | 接近，来自最近 300 条动态 |
| GraphQL 贡献日历 | 是 | 视个人主页设置而定 | 是 |

## 在两次构建之间保持更新

实时轮询只对开着页面的人有效。为了让其他访客看到的静态 HTML 也保持新鲜，一个定时运行的 GitHub Actions 工作流每隔几个小时重新构建一次网站。两者结合起来，正在浏览的读者最多落后一分钟，新访客最多落后几个小时。

## 接下来我会改进什么

如果网站规模变大，我会把快照移到一个带短时缓存的边缘函数里，让所有访客共享同一次 GitHub 请求，而不是各自请求。就目前而言，静态版本速度快、托管免费，而且没有任何会宕机的部分。
