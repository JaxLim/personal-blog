首页上有一条活动轨迹，记录了我最近十三周的所有推送，旁边还有一行字显示我的最新动态。只要页面开着，它们就会自动刷新。背后没有服务器、没有数据库，也没有接收 Webhook 的服务，整个网站就是一堆静态 HTML。

这篇文章讲讲它是怎么实现的，以及我为什么选了这种结构。

## 两部分：快照和增量更新

数据分两步到达页面。

1. **每次构建之前**，一个小脚本调用 GitHub API，把结果与上一次保存在 `src/data/github.json` 中的副本合并，再由 Astro 直接渲染进 HTML。即使访客关闭了 JavaScript，也能看到完整的页面，搜索引擎收录的也是真实内容。
2. **在浏览器里**，一个小模块从快照接手，向 GitHub 查询构建之后的新动态，再合并到页面上。

快照以 JSON 的形式嵌入页面，浏览器不需要再请求一次：

```astro
---
const json = JSON.stringify(data).replace(/</g, '\\u003c');
---
<script is:inline type="application/json" id="github-data" set:html={json} />
```

转义 `<` 很重要：否则只要某条提交信息里含有 `</script>`，这个标签就会被提前截断。

## 克制地轮询

GitHub API 对匿名请求的限制是每个 IP 每小时 60 次。要是页面每隔几秒就轮询一次，几分钟就会把额度耗光，所以这个模块守着几条规矩。

### 条件请求

每个响应都带有 `ETag`。下一次请求时把它放进 `If-None-Match` 发回去，如果内容没有变化，GitHub 会返回空的 `304 Not Modified`。

```ts
const headers: Record<string, string> = { Accept: 'application/vnd.github+json' };
const etag = state.etags[path];
if (etag) headers['If-None-Match'] = etag;

const res = await fetch(API + path, { headers, cache: 'no-cache' });
if (res.status === 304) return null; // 没有新内容
```

### 让 GitHub 决定节奏

动态接口会返回 `X-Poll-Interval` 响应头，通常是 60 秒。轮询间隔永远不会短于这个值；模块还会读取 `X-RateLimit-Remaining`，额度快用完时就彻底停下。

### 没人看时就暂停

标签页切到后台时，轮询就停下；读者切回来时，如果已经过了间隔时间，就马上补查一次。

<Callout type="tip" title="为什么不用 Webhook？">
Webhook 是即时的，但需要一台服务器来接收，还需要某种方式把变化推送给打开的页面。对个人网站来说，用一分钟的延迟换来不用维护任何基础设施，很划算。
</Callout>

## 让轨迹的数据靠得住

这条轨迹统计的是*贡献*，而不只是提交：一次推送按其中的提交数计算，发起 PR、提 Issue 或发布版本各算一次。给别人的仓库点 Star 不算。

如果构建时提供了 GitHub token，脚本会改用 GraphQL API 获取精确的贡献日历，也就是 GitHub 个人主页上那片绿格子的数据；如果主页设置了显示私有贡献，私有仓库的贡献也会算进去。

| 数据来源 | 需要 token | 包含私有仓库 | 每日数据准确 |
| --- | --- | --- | --- |
| 公开动态 API | 否 | 否 | 接近，来自最近 300 条动态 |
| GraphQL 贡献日历 | 是 | 视个人主页设置而定 | 是 |

## API 悄悄变了的时候

做这个网站的时候，主页上最近几次推送突然都变成了“推送到 main”，既没有提交信息，提交数也是零。我的代码一行没动，原来是 GitHub 的事件 API 不再在推送事件里附带提交列表了。

修复的原则是：原本省事的地方，修完也要一样省事。每个推送事件仍然带有推送前后的两个提交 ID，所以构建脚本用 compare API 查这一段区间；但只查最新的 20 次推送，每个事件也只查一次，结果跟事件存在一起，之后的构建不会重复请求。

```js title="scripts/fetch-github.mjs"
const cmp = await gh(`/repos/${repo}/compare/${before}...${head}`);
event.payload.enriched = {
  count: cmp.total_commits, // [!code highlight]
  message: cmp.commits.at(-1)?.commit.message.split('\n')[0] ?? null,
};
```

那天下午还顺手定了两条规矩。一是仓库、事件、贡献日历这几个数据源分开获取，哪个失败了，就只有它沿用之前保存的数据。二是保存的文件要提交进仓库，这样即使构建时断网，显示的也还是真实数据，只是旧一点。只要设置了用户名，网站就绝不会拿假数据充数。

## 在两次构建之间保持更新

实时轮询只对开着页面的人有用。为了让新访客拿到的静态 HTML 也不至于太旧，我用一个定时的 GitHub Actions 工作流每隔几小时重新构建一次。两者结合，正在浏览的读者最多延迟一分钟，新访客最多延迟几个小时。

## 接下来我会改进什么

如果网站规模变大，我会把快照移到一个带短时缓存的边缘函数里，让所有访客共享同一次 GitHub 请求，而不是每人各请求一次。就现在来说，静态方案速度快、托管免费，也没有哪个环节会宕机。
