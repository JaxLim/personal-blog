このサイトのホームには、過去 13 週間にプッシュしたものすべてを記録したトレースと、最新のアクティビティを伝える一行があります。どちらも、ページを開いている間は自動で更新されます。裏側にサーバーもデータベースも Webhook の受け口もありません。サイトはただの静的な HTML です。

この記事では、その仕組みと、ほかの方法ではなくこの形を選んだ理由を説明します。

## スナップショットとストリーム

データは二段階でページに届きます。

1. **ビルド時**に、Astro が GitHub API を一度だけ呼び出し、リポジトリと最近のアクティビティを取得して HTML に直接書き出します。JavaScript を無効にしていても完全なページが表示され、検索エンジンにも実際の内容がインデックスされます。
2. **ブラウザでは**、小さなモジュールがスナップショットの続きを引き受けます。ビルド以降の新しいアクティビティを GitHub に問い合わせ、ページに反映します。

スナップショットは JSON としてページに埋め込まれているので、ブラウザがもう一度取得する必要はありません。

```astro
---
const json = JSON.stringify(data).replace(/</g, '\\u003c');
---
<script is:inline type="application/json" id="github-data" set:html={json} />
```

`<` のエスケープは重要です。これがないと、終了 script タグを含むコミットメッセージによって、タグが途中で閉じられてしまいます。

## 行儀のよいポーリング

GitHub API の匿名リクエストは、IP アドレスごとに 1 時間あたり 60 回までに制限されています。数秒おきにポーリングすれば数分で使い切ってしまうので、このモジュールはいくつかのルールに従います。

### 条件付きリクエスト

レスポンスにはすべて `ETag` が付いています。次のリクエストでそれを `If-None-Match` として送り返すと、変更がなければ GitHub は中身のない `304 Not Modified` を返します。

```ts
const headers: Record<string, string> = { Accept: 'application/vnd.github+json' };
const etag = state.etags[path];
if (etag) headers['If-None-Match'] = etag;

const res = await fetch(API + path, { headers, cache: 'no-cache' });
if (res.status === 304) return null; // 新しいものはない
```

### ペースは GitHub に任せる

イベント API は `X-Poll-Interval` ヘッダーを返します（通常は 60 秒）。ポーリングがそれより頻繁になることはなく、`X-RateLimit-Remaining` を見て残りが少なくなれば完全に止まります。

### 誰も見ていないときは止める

タブが非表示になると、ポーリングは止まります。読者が戻ってきたとき、間隔が過ぎていればすぐに追いつきます。

<Callout type="tip" title="なぜ Webhook を使わないのか">
Webhook なら即時に反映されますが、受け取るサーバーと、開いているページに変更を届ける仕組みが必要です。個人サイトなら、1 分の遅れと引き換えにインフラを一切運用しないほうが割に合います。
</Callout>

## 信頼できるトレースにする

このトレースが数えているのはコミットだけではなく、*コントリビューション*です。プッシュは含まれるコミット数で数え、プルリクエストの作成、Issue の起票、リリースの公開はそれぞれ 1 件として数えます。他人のリポジトリにスターを付けても数えません。

ビルド時に GitHub のトークンがあれば、代わりに GraphQL API から正確なコントリビューションカレンダーを取得します。GitHub のプロフィールに並ぶ緑のマス目と同じデータで、プロフィールで表示する設定にしていれば非公開のコントリビューションも含まれます。

| データソース | トークン | 非公開の作業 | 日ごとの正確さ |
| --- | --- | --- | --- |
| 公開イベント API | 不要 | 含まない | 直近 300 件からの近似 |
| GraphQL カレンダー | 必要 | プロフィールの設定次第 | 正確 |

## ビルドとビルドの間も新しく保つ

ライブのポーリングが役立つのは、ページを開いている人だけです。それ以外の訪問者にも新しい HTML を届けるため、GitHub Actions のスケジュール実行で数時間ごとにサイトを再ビルドしています。この二つを組み合わせることで、閲覧中の読者には最大 1 分、新しい訪問者にも最大数時間の遅れで最新の状態を届けられます。

## 次に変えたいこと

サイトが大きくなったら、スナップショットを短時間キャッシュするエッジ関数に移し、訪問者がそれぞれ GitHub にリクエストするのではなく、一つのリクエストを共有するようにするつもりです。今のところは、静的なままのほうが速く、ホスティングも無料で、落ちる部分が何もありません。
